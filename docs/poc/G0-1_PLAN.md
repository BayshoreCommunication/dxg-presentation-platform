# G0-1 plan — can the Room Agent drive PowerPoint reliably?

Status: PLAN, 2026-09-28. Gate definition: `docs/PHASE0_GATE.md` §G0-1 (16-item matrix, both OS targets, DXG
fidelity sign-off). Decision under test: D-002 (Electron/Node agent, PowerPoint via COM; fallback: an
out-of-process helper). Report when done: `docs/poc/ROOM_AGENT_POC.md`.

## What G0-1 is — and is not

G0-1 answers one question: **can software we write open, run, supervise and clean up PowerPoint slideshows on a
room PC reliably enough for a live event?** It is a proof of concept with evidence, not the finished Room Agent.
Sync (G0-2), the MSI installer and auto-update (G0-1b design only, M5-6), and the fleet dashboard are out of scope.

What the platform has today: device keys and heartbeats (`/api/v1/agent/heartbeat`, `rooms/:id/device-key`), a
staff-side room view with a Launch that only *records* a launch (D-108), and a server-simulated sync. No agent app,
no manifest/download endpoints, no test corpus.

## Approach: build everything testable without Windows first, then run the matrix on Windows

### Phase A — build (no Windows needed; ~1–1.5 engineer-weeks)

| # | Piece | What it is | How it is tested before Windows |
|---|---|---|---|
| A1 | `apps/room-agent` skeleton | Electron app: main process (supervisor, IPC), a full-screen **holding screen** window per chosen monitor, a local SQLite launch log | Runs on macOS; holding screen on a chosen display |
| A2 | **Playback driver interface** | `open(file) → start show on monitor N → status → close`, plus crash and hang events. Three implementations: **COM in-process** (`winax`), **helper process** (PowerShell script driving `PowerPoint.Application` over COM, one process per launch, JSON over stdio), **fake** (for Mac/CI) | Contract tests run against the fake; the same tests run against the real drivers on Windows |
| A3 | **Supervisor** | Watches the PowerPoint process: crash detected ≤5 s → relaunch or holding screen ≤10 s; never a bare desktop; kills orphaned PowerPoint/COM processes; queues or rejects a second launch while a show is running (items 9–11, 15, 16) | Fault injection against the fake driver (crash, hang, slow start) |
| A4 | **Launch rules** | Only a file that is present, SHA-256-verified and allowed may launch; anything else shows the holding screen and is logged (BUILD_SPEC §8) | Unit tests |
| A5 | **Test corpus (G0-7)** | ≥30 synthetic decks: animations and transitions, embedded video (H.264/HEVC/ProRes), linked video, missing linked video, custom and missing fonts, 16:9 and 4:3, legacy .ppt and .pptx, macro-enabled .pptm, external links, a corrupted file, plus PDF/KEY/video/image for item 7. Generated by script (python-pptx + LibreOffice) where possible; the few that need PowerPoint itself are made once on the Windows box. Catalogued in `tests/fixtures/g0-1/MANIFEST.md` | Files open in LibreOffice; manifest complete |
| A6 | **PoC harness** | One command per matrix item that runs the scripted part and writes evidence (JSON logs, timings, process lists, memory samples) to `docs/poc/evidence/<os>/<item>/` — e.g. 100 launch/close cycles with P95 timing, orphan-process count, 72-hour soak sampler (memory, handles, PowerPoint processes every minute) | Harness runs end to end against the fake driver |
| A7 | **Report template** | `docs/poc/ROOM_AGENT_POC.md` with the pinned-versions table and one PASS/FAIL row per item, filled from the evidence | — |

### Phase B — run the matrix on Windows (~1–2 weeks, includes the 72-hour soak)

1. Set up both targets (below). Record Windows build, Microsoft 365/PowerPoint build, Electron, Node and `winax`
   versions, CPU (x64).
2. Run items 1–16 with the **COM in-process** driver on Windows 11, then Windows 10.
3. Any item that fails: re-run with the **helper-process** driver.
4. Fidelity items (4 animations, 5 media, 6 fonts) need a person watching: screen recordings of each corpus deck
   played by the agent vs. opened by hand in PowerPoint.
5. Start the 72-hour offline soak (item 14) on each target; network unplugged, scheduled launches every few minutes.
6. Fill in `ROOM_AGENT_POC.md`; DXG watches a fidelity demo and signs off.

**Outcome rules (from the gate):** all 16 pass with COM → D-002 accepted as written. Failures that the helper fixes
→ D-002 amended (Electron shell + helper). Both fail → **stop**, re-decide the agent architecture with DXG.

### Phase C — only after G0-1 passes (this is M5-3, not G0-1)

Make the staff **Launch** button real: the agent picks up launch commands (on its heartbeat/poll, so it works the
same online and offline), launches through the chosen driver, and reports back; the room view shows what actually
happened. Plus the manifest/download endpoints (G0-2) so files arrive on the room PC by themselves.

## What we need that only you can provide

1. **Windows 11 PC** (physical, x64) with **Microsoft 365 PowerPoint**, and **3 monitors** available (item 3 needs a
   2- and a 3-monitor setup).
2. **Windows 10 test machine or VM** with Microsoft 365. The gate names Windows 10 21H2; that version is out of
   support, so this should really match whatever DXG's room PCs run (G0-4 fleet profile) — worth confirming.
3. A **standard (non-admin) Windows account** on each for the agent (the gate requires no admin rights).
4. **A way for the tests to be run**: either someone at the machine runs one command per item, or the PC gets
   OpenSSH Server so the scripted items can be run remotely (visual checks still need a person or a recording).
5. **DXG's room-PC profile** if available (Windows/Office versions, admin rights, antivirus, monitor setup) — it
   decides the real targets and whether antivirus interferes with COM automation.
6. Approval for any purchases (Microsoft 365 licences, a Windows licence for the VM).

## Risks to watch

- **COM from Node (`winax`) is the known risk** (ROADMAP R1): native module builds against Electron's Node version,
  and COM calls can hang. The helper-process driver exists from day one for this reason.
- **Antivirus / endpoint protection** on DXG PCs can block scripted Office automation or PowerShell.
- **Microsoft 365 updates** change PowerPoint builds under us — pin and record the build; re-run a smoke subset after
  updates.
- **Presenter view and monitor targeting** behave differently across PowerPoint builds and display setups (item 3).
- **The 72-hour soak can only start once everything else passes**, so it sets the finish date.

## Estimate

Phase A about 1–1.5 engineer-weeks (can start now). Phase B about 1–2 weeks once the hardware exists, dominated by
the two 72-hour soaks and the fidelity recordings. Phase C is scheduled in M5 after the gate passes.
